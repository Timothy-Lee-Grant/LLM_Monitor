01

The thirty-second model

Three nouns, in a fixed order. Everything else in Docker is detail hanging off them.

A Dockerfile is a recipe — a text file of build steps. A image is what the recipe bakes: a frozen, read-only filesystem snapshot with a startup command baked in. A container is one running instance of an image — the image plus a writable scratch layer, a process, an IP address, and a lifespan.

The relationship is one-way and one-to-many. A Dockerfile builds an image. An image can start any number of containers. A container can never modify its image. Delete every container and the image is untouched; that is precisely why your five images survive a docker compose down.

Your project adds a fourth noun that isn't part of Docker itself: Compose. docker-compose.yaml is a cast list. It names 16 services, and a service is a set of instructions for producing containers — which image to use or build, what to name the container, which ports to publish, what to mount. Compose is the layer that turns "run sixteen docker run commands with the right flags in the right order" into one command.

02

A service is not a thing — it produces things

Your question, answered

When you write a service name in docker-compose.yaml, you have created neither an image nor a container. You've written a recipe entry. When you run build, that entry produces an image whose name Compose derives from yours. When you run up, that image produces a container whose name Compose derives from yours too — unless you overrode it with container_name:, which you did for every service in this project.

So one service name shows up in up to three places on your screen, spelled three different ways. That is the single biggest source of the confusion.

The three naming rules

Learn these and the screens stop being mysterious.

  1. Image name (only for services with build:) = <project>-<service key>. Your project name is llm_monitor, set explicitly by -p "$PROJECT" in build.sh. Service key dotnet_server → image llm_monitor-dotnet_server:latest. That's the truncated llm_monitor-dotnet_serv… row on your Images tab.
  2. Container name = whatever container_name: says. You set one on every service, so the names are exactly as written — dotnet_server, langchain_service, toolbox, openwebui, pgvector_service. Without container_name:, Compose would have generated llm_monitor-dotnet_server-1 instead.
  3. Volume name = <project>_<volume key>. Volume key pgdata → llm_monitor_pgdata. Exactly what your Volumes tab shows.

Watch thisYour service key is pgvector-service with a hyphen, but its container is named pgvector_service with an underscore, because container_name: says so. Compose commands take the service key (docker compose logs pgvector-service); plain Docker commands take the container name (docker logs pgvector_service). Mixing them up is the most common "no such service" error you will hit.

Why your .NET image is only 287 MB

Because server/dockerfile is a multi-stage build, and this is the single most useful Dockerfile idea to internalize:

# STAGE 1 — has the whole SDK, compilers, NuGet cache
FROM mcr.microsoft.com/dotnet/sdk:11.0-preview AS build-env
COPY *.csproj ./
RUN dotnet restore --no-cache
COPY . ./
RUN dotnet publish -c Release -o /app/publish

# STAGE 2 — a fresh, much smaller base
FROM mcr.microsoft.com/dotnet/aspnet:11.0-preview
COPY --from=build-env /app/publish .   # ← reach back, take only the output
ENTRYPOINT ["dotnet", "server.dll"]

Only the last FROM becomes your image. Stage 1 — SDK, source, intermediate build junk, several gigabytes of it — is thrown away, and the one highlighted line copies the compiled output across the boundary. That's how a .NET service ends up smaller than a Python one.

Layer caching, and why the COPY order matters

Each instruction in a Dockerfile makes a cached layer. Docker reuses a layer if that instruction and its inputs are unchanged; the moment one changes, that layer and everything after it rebuild. Both your Dockerfiles exploit this the same way — dependencies first, source second:

COPY requirements.txt requirements.txt
RUN pip install --no-cache-dir -r requirements.txt   # slow layer
COPY . .                                             # fast layer, changes constantly

Edit a Python file and only the last line reruns. Reverse the two and every one-character edit reinstalls every dependency. This is why langchain_service took 1m 11s to build the first time and would take seconds on a source-only change.

On that "0 Bytes in use"The Images tab header reads 4.84 GB / 0 Bytes in use with Last refresh: 22 minutes ago beside it — a stale count, taken before your containers started. Click the refresh arrow and it will attribute the in-use bytes properly. Relatedly, you have no dangling <none> images cluttering the list because build.sh ends with docker image prune -f, which deletes images no container references.

It is the Compose project group — Docker Desktop collapses every container that shares a project label into one expandable row. The blanks are blank because a group has no single ID, image, or port. 05

The Builds tab: two rows, and a name that isn't a service

Build history shows server (35.6s) and langchain_service (1m 11s). Two rows for sixteen services, because only two services have a build: key — everything else pulls a prebuilt image and never touches the builder.

Now the detail that trips people: the first row says server, but you have no service called server. The Builds tab names a build after its build context directory, not the service. Look at the YAML:

dotnet_server:          # ← service key → image name
  build:
    context: ./server       # ← folder → Builds tab name
    dockerfile: dockerfile

langchain_service matches only because its folder happens to share the service's name. So that's a fourth naming source: service key, container_name, volume key, and now build context folder.

The context is also a real functional boundary. It is the set of files shipped to the build daemon, and COPY can only see inside it — which is why server/dockerfile writes COPY *.csproj ./ and not COPY server/*.csproj. The paths are relative to ./server, not to the repo root.

Builder: desktop-linux on both rows is the BuildKit instance inside Docker Desktop's VM. Author: N/A just means you weren't signed in to Docker Hub. Neither indicates a problem, and both green checkmarks mean the builds succeeded.

06

Volumes: the only things that survive

A container's writable layer dies with the container. Anything that must outlive --force-recreate — and build.sh recreates every container on every run — has to live in a volume: a directory managed by Docker, outside any container, mounted into one at a path you choose.

The syntax is volume_name:/path/inside/container. Your three:

Volume on your screenDeclared asMounted intoSizeHolds
llm_monitor_openwebui_data openwebui_data:/app/backend/data openwebui 264.2 MB Accounts, chat history, settings. Delete this and your admin@localhost login is gone.
llm_monitor_pgdata pgdata:/var/lib/postgresql/data pgvector_service 46 MB The whole Postgres cluster — your embeddings and RAG documents.
llm_monitor_fastembed_cache fastembed_cache:/tmp/fastembed_cache langchain_service 0 Bytes Should hold a ~100 MB ONNX embedding model — see below.

That 0 Bytes is a fact, not a bugThe fastembed cache is empty because you are running in mock mode. That model is only downloaded by the openai_compat CPU embeddings provider in live mode. An empty volume here is exactly what a healthy mock run looks like — and the first live run will fill it, then keep it filled across restarts, which is the entire reason the volume exists.

A second kind of mount, which isn't in the tab

Volumes aren't the only thing that can be mounted. Compare these two lines from your file:

volumes:
  - pgdata:/var/lib/postgresql/data                              # named volume
  - ./scripts/init.sql:/docker-entrypoint-initdb.d/init.sql:ro   # bind mount

The first is a named volume — Docker owns the storage, and it appears in the Volumes tab. The second is a bind mount — a path on your Mac projected into the container, owned by you, and it never appears in the Volumes tab at all. That's why your observability configs (./observability/prometheus.yml, the Grafana provisioning folders) are invisible there even when running: they're bind mounts, not volumes. The :ro suffix makes them read-only inside the container.

Practical consequence: editing scripts/init.sql on your Mac changes what the container sees immediately, because it's the same file. Changing something inside pgdata requires going through Postgres.

One more trap worth knowing now rather than later: init.sql runs only when the data directory is empty — i.e. on a brand-new pgdata volume. Editing it after the fact does nothing until you delete the volume. docker compose down leaves volumes alone by design; docker compose down -v is what wipes them.

07

Ports, in both directions

A container gets its own network namespace — its own private IP, its own full set of 65535 ports. Nothing on your Mac can reach any of them unless you explicitly publish one. That's what ports: does, and the order is always HOST:CONTAINER.

dotnet_server:
  ports:
    - "5000:8080"
       ↑     ↑
       │     └── the port the app listens on inside the container
       └──────── the port you type into your browser on the Mac

The container side is fixed by the app: ASP.NET defaults to 8080 (which is why the Dockerfile says EXPOSE 8080), gunicorn binds 0.0.0.0:5000 in your entrypoint, OpenWebUI serves on 8080. The host side is yours to choose, and its only constraint is that no two services may claim the same one — which is exactly why your file has that trail of comments about 3000 being OpenWebUI, 3001 Grafana, 3002 Langfuse.

ServiceMappingYou typeNote
openwebui3000:8080localhost:3000Your front door.
dotnet_server5000:8080localhost:5000The gateway, same container port as OpenWebUI — no conflict, different containers.
langchain_service5001:5000localhost:5001Dev/test bypass. Deleting this line is your production lockdown switch.
toolbox8090:8090localhost:8090Voxel viewer socket only — human-eyes-only channel.
toolbox (MCP)— none —unreachable from MacPort 8080 has no mapping on purpose. Tool execution stays on the internal network.
pgvector-service— none —unreachable from MacPostgres is fully internal. To use psql, go through the container.

Note what "no ports:" does not mean. Postgres is running and listening on 5432 right now, and langchain_service talks to it constantly. It's simply invisible from outside the Docker network. Absence of a port mapping is a security posture, not a disabled service — and your file uses it as one twice, deliberately.

To get a shell on the internal-only database anyway:

docker exec -it pgvector_service psql -U admin -d vectordb

docker exec runs a new process inside an already-running container, so it lands on the inside of the network boundary and needs no published port.

08

The network you can't see in Docker Desktop

Your Docker Desktop sidebar has Containers, Images, Volumes, and Builds — but no Networks tab. Compose still created one: llm_monitor_default. Every service joined it automatically, and it is the reason your system works at all.

On that network, the service key is a DNS hostname. Not the container name, not the image — the service key from the YAML. Docker runs an embedded DNS server that resolves it to the container's current IP.

// server/appsettings.json — YARP's upstream
"Destinations": { "primary": { "Address": "http://langchain_service:5000/" } }

Two things about that URL are worth sitting with:

  • langchain_service is the compose service key, resolved by Docker's DNS.
  • The port is 5000, the container-side port — not 5001. Port mappings do not exist on the internal network. Containers always talk to each other on the real, unmapped ports.

The same pattern runs through the rest of your environment variables: http://toolbox:8080/mcp (a port with no host mapping at all), http://dotnet_server:8080/v1 (8080, not 5000), langfuse-postgres:5432, http://ollama:11434.

The classic failurelocalhost inside a container means that container, not your Mac and not another service. If OPENAI_API_BASE_URL said http://localhost:5000/v1, OpenWebUI would search its own filesystem for a gateway and fail with connection refused. Inside the compose network: use service names. From your Mac's browser or terminal: use localhost plus the host-side port. Two different address spaces, and every "it works in my browser but the container can't reach it" bug lives in the gap between them.

Also note AllowedHosts=localhost;127.0.0.1;toolbox on the toolbox service. Because callers address it as toolbox, that literal name has to appear in its Host-header allowlist or every request comes back 400. A DNS name isn't just plumbing — it becomes part of the HTTP request.

To see the network Docker Desktop won't show you:

docker network ls
docker network inspect llm_monitor_default   # every container + its internal IP

build: versus image: — and having both

Each service answers one question: where does my image come from?

build: — bake it here

Compose runs a build from your source and names the result llm_monitor-<service>. Your code changes are only picked up by a rebuild.

Two services: dotnet_server, langchain_service.

→ appears in Builds tab + Images tab

image: — download it

Compose pulls the named tag from a registry, if it isn't already local. No build, no Builds row.

Fourteen services, including your own toolbox, which is built in a separate repo and consumed here as a published artifact.

→ appears in Images tab only

Tags are the version, and floating tags bite

The part after the colon is the tag. pgvector/pgvector:pg16 and ghcr.io/open-webui/open-webui:0.10.2 are pinned; ollama/ollama:latest and the observability images are floating. A floating tag means the image you get today and the image you got last month may differ with nothing in your repo to show for it — which is precisely the reasoning in your own comment on the OpenWebUI pin. latest is not a promise. It's just the default label.

Your release override, which uses both keys at once

docker-compose.release.yml adds an image: to the two services that already have build::

services:
  dotnet_server:
    image: ghcr.io/timothy-lee-grant/llm_monitor-gateway:${LLM_MONITOR_VERSION:-latest}

Holding both is deliberate and it's the standard Compose idiom. docker compose build still builds from source and tags the result with that registry name; docker compose pull / up fetch the published image and never invoke a build. One file, two modes: developing on source, or running someone's published release. Applied by stacking files, later ones winning:

docker compose -f docker-compose.yaml -f docker-compose.release.yml up

That's the same layering mechanism as the ${GPU} string injector your build.sh has a TODO about — -f flags are read in order and merged, so a later file overrides keys set by an earlier one.

Startup order, and why "started" isn't "ready"

Containers start in parallel unless told otherwise. depends_on imposes order — but the plain form is weaker than it looks:

openwebui:
  depends_on:
    - dotnet_server        # waits for the container to EXIST. That's all.

langchain_service:
  depends_on:
    pgvector-service:
      condition: service_healthy   # waits for the healthcheck to PASS
    toolbox:
      condition: service_healthy

A Postgres container exists within milliseconds and is ready to accept queries several seconds later. Without condition: service_healthy, your ingestion would fire into a database still starting up. That's the whole reason the healthchecks exist.

A healthcheck is just a command Docker runs inside the container on a schedule; exit 0 means healthy. Yours are shaped by what each image actually ships:

  • toolbox — curl -f http://localhost:8080/health. Here localhost is correct: the check runs inside that container.
  • langchain_service — a stdlib Python one-liner, because python:3.11-slim ships neither curl nor wget. The image constrains the probe.
  • pgvector-service — pg_isready, the tool Postgres provides for exactly this.

start_period: 20s on langchain is grace time: failures during it don't count against retries. It has to cover image boot plus the one-time RAG ingestion your entrypoint runs before gunicorn starts. When you expand the group row in Docker Desktop, the health state shows next to each container — that's this machinery surfacing.

The dependency chain your file describes, end to end:

pgvector-service ─┐
                  ├─(healthy)→ langchain_service ─(healthy)→ dotnet_server ─(started)→ openwebui
toolbox ──────────┘

The eleven services that aren't there

Here's the arithmetic that explains all four of your screens at once.

16services defined
5with no profile
10profile: obs
1profile: local-live

A service carrying profiles: ["obs"] or ["local-live"] is inert unless that profile is activated. Not stopped — never created. No container, no image pulled, no volume made. It is as if those lines weren't in the file.

So: five profile-free services → five containers → five images, one apiece, none shared. Your screens agree exactly.

And the volumes: nine are declared, three exist. The six missing ones (ollama_data, prometheus_data, grafana_data, langfuse_pg_data, clickhouse_data, minio_data) all belong to profiled services. A volume is created lazily, when a container first needs it. Declaring one costs nothing.

Activation is a flag:

./build.sh --obs                       # → --profile obs → 10 more containers
docker compose --profile local-live up  # → ollama joins
docker compose --profile "*" down       # → every profile, so nothing is orphaned

That last one is the first real command in build.sh, and the "*" matters: down without it only tears down profile-free services, leaving obs containers from a previous run alive and confusing.

Run ./build.sh --obs and Docker Desktop changes dramatically — 15 containers in the group, ten more images pulled, five new volumes. Nothing about your YAML changed; you only turned on a subset.

12

build.sh, line by line

Every artifact on your screen was produced by this script. Reading it in order is the fastest way to connect the two.

docker compose -p llm_monitor --profile "*" down --remove-orphans

Stops and deletes every container in the project, across all profiles, plus any left over from a config that no longer exists. Volumes survive — down never removes them without -v. This is why your chat history and embeddings outlast every rebuild.

docker compose -p llm_monitor -f docker-compose.yaml build

Builds the two services with build:, using the layer cache. Result: two rows in Builds, two refreshed llm_monitor-* images. Nothing else is touched.

docker compose -p llm_monitor -f docker-compose.yaml up --force-recreate -d

Creates and starts containers in dependency order, pulling any missing registry image first. --force-recreate replaces containers even if their config is unchanged — which discards each container's writable layer, making the volume boundary from §06 the thing that decides what you keep. -d detaches so the containers keep running after the script exits.

docker image prune -f

Deletes dangling images — the previous llm_monitor-* builds, now untagged because the new build took their names. This is why your Images tab is a clean five rows with no <none> entries, and why disk usage doesn't creep with every rebuild.

Where the environment goes

Three layers feed values into containers, and it helps to see them as a chain:

build.sh    export LLM_MODE="$MODE"
              ↓
compose     - LLM_MODE=${LLM_MODE:-mock}        # shell var, else default
              ↓
container   os.environ["LLM_MODE"]

${VAR:-default} reads from your shell or the .env file next to the compose file, falling back to the default. Note the deliberate difference between ${LLM_MODE:-mock} and ${AZURE_OPENAI_API_KEY:-}: the second defaults to an empty string, which your factory's _require_env treats as missing and fails loudly on. Empty-as-default is a design choice — it converts a silent misconfiguration into a startup crash with a message.

Two more things follow from this. Environment values are read at container creation, so changing .env requires up again, not just a restart. And docker inspect dotnet_server will print the fully resolved environment — including any secrets — which is worth remembering before pasting that output anywhere.

14

The confusions, settled

Is my service name an image or a container?

Neither. It's a recipe key. It becomes the image name (prefixed with the project) if the service builds, and it becomes the container name unless container_name: overrides it — which in your project it always does. It also becomes the DNS hostname other containers use, and that one is never overridden by container_name.

Quick answers

  • Where did my code change go? Into the image only after build. Compose's up alone will happily restart the old image. Your build.sh always does both, in order.
  • Why is my image huge? Base image plus dependencies, almost always. Multi-stage builds fix compiled languages; interpreted stacks are dominated by their package installs.
  • Why can't the container reach my Mac's localhost? Because localhost is the container. Use host.docker.internal to reach the Mac, or a service name to reach a sibling.
  • Why did my data vanish? It wasn't in a volume, or you ran down -v. Container filesystems are disposable by design.
  • Why is a port "already allocated"? Two things want the same host-side port. Change the left number; the right one belongs to the app.
  • Why is a service missing? Check for a profiles: key before anything else.
  • Which name do I pass to a command? docker compose <cmd> pgvector-service (service key, hyphen). docker <cmd> pgvector_service (container name, underscore).

The four screens, in one sentence each

  • Images — the frozen templates you have on disk, built here or pulled. They outlive containers.
  • Containers — running instances, grouped by Compose project. Ephemeral by design.
  • Volumes — the only storage that survives a recreate. Created lazily, named <project>_<key>.
  • Builds — the history of images baked from your source, named after the build context folder.
